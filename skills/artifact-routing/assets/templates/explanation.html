Why Driftwood rotates on size and time

In one minute

This page answers one question: why does Driftwood rotate a Live log when it is above max_size or when the schedule time is reached, and not on time alone? The answer is that a time-only rule lets a file grow by the write rate times the whole period, while the size rule caps growth at max_size plus one check interval of writes. The price is that Generation names carry a number instead of a calendar period (L1). In the sample figures below, a daily schedule allows up to 216 GB in one file and the size rule allows about 200 MB. We ask the maintainers to review ADR-1. Two questions are open: Q1 with the config format owner and Q2 with the release owner.

Logs grow in bursts, not on a calendar

A service that writes a few kilobytes an hour can write megabytes per second for a few minutes when it retries a failing dependency. A rotation rule that only looks at the clock cannot see that difference. This page explains the rule the Driftwood 2.4.0 CLI uses instead. Its settings live in a TOML file, driftwood.toml. The page does not explain how to configure the rule or list every option.

Two goals and no more drive the design. Each has a name so later sections can cite it.

  • G1. Bounded disk use. No single log file may fill the volume between two rotations.
  • G2. Predictable retention. The keep option counts Generations, so the number of files on disk stays fixed.

Interpretation, not measurement: we read G1 as the more important goal because a full volume stops the service, while an odd file name only costs a reader some time. Nothing on this page proves that ranking for every team.

Two triggers share one check, so the earlier one wins

Your scheduler calls driftwood run every minute [SAMPLE]. Each call asks two questions about every configured file. If the Live log is above max_size the Size trigger fires. If the schedule time is reached the Time trigger fires. Either one rotates the file, and the first to fire wins because rotation resets both.

The size trigger matters because of how far a file can grow before the next Rotation. With a write rate r, a schedule period P and a check interval c, the worst-case file size is:

  • Time only: r × P.
  • Size and time: max_size + r × c.

Recompute with the sample inputs r = 2.5 MB/s, P = 86400 s (daily) and c = 60 s, max_size = "50MB" [SAMPLE]:

$ python -c "print(2.5*86400/1000, 'GB', 50+2.5*60, 'MB')"
216.0 GB 200.0 MB

The same 2.5 MB/s burst under the size rule looks like this over time. The overshoot is one check interval of writes, so it does not depend on the schedule.

A shorter time-only schedule still loses to the burst

Four ways to bound disk use were compared against G1 and G2. The table gives the final verdict for each.

OptionWhat it givesWhat it costsVerdict
Do nothing, leave rotation to each applicationNo new toolEvery service rotates differently and many do not at allLoses on G1 and G2
Time only, short periodCalendar names, simplest ruleThe period must be tuned to the worst burst, and a file still grows by r × PStrongest alternative, loses on G1
Size onlyHard cap on file sizeA quiet service never rotates, so old lines never reach compress or keepLoses on G2
Size and time, whichever firstCap on size and a bound on ageGeneration names carry a number, not a period (L1)Chosen

The strongest alternative is time only with a short period, because it keeps names predictable and needs one rule. It loses because its bound depends on guessing the worst burst: a 5 minute period still allows r × 300 s = 750 MB at the sample rate, and a quiet hour pays the cost of a Rotation it did not need. The size trigger bounds the file by volume, whatever the period. Time only does win on one point: names. A reader who wants "the log for Tuesday" finds it directly under a time-only rule and has to check file times under ours.

The price is paid by people who search archives by date

Positive consequences go to the operator on call, who no longer sees a full volume from logs. Negative consequences go to whoever reads Generations later. Three limits are accepted.

  • L1. Numbered names. A Generation name carries a number, not a calendar period, so a day may span several Generations.
  • L2. Check granularity. A Live log can exceed max_size by one Check interval of writes, the Overshoot. Lowering the interval lowers the overshoot and raises the number of runs.
  • L3. Rename window. Rotation renames the Live log, and the application keeps writing to the renamed file until it reopens its log, so lines can land in Generation 1 after the Rotation [SAMPLE]. A service that reopens its log on a signal avoids it.

Two cases show where the claim stops holding. A service that writes one line a day never reaches max_size, so only the Time trigger acts and the size rule is irrelevant for it. A file Driftwood cannot read ends the run with error: permission denied on /var/log/app, and then neither trigger can act, so G1 is not met until the permission is fixed.

Limit

The bound in G1 holds only while driftwood run is actually called. If the scheduler stops, both triggers stop.

ADR-1 records the choice of two triggers

ADR-1. Rotate on size and on time.

Status: Accepted · Date: 2026-10-28 · Decided by: Driftwood maintainers · Supersedes: none [SAMPLE]

The record follows the ADR shape: context, decision, options, consequences, revisit condition.

  • Context. A burst of 2.5 MB/s fills 216 GB in one day under a daily rule [SAMPLE]. Goals G1 and G2 apply.
  • Decision. We will rotate a file when it reaches max_size or when its schedule is due, whichever comes first.
  • Options. Compared in the alternatives table: do nothing, time only, size only, size and time.
  • Consequences. Positive: bounded files, fixed Generation count. Negative: L1, L2, L3.
  • Revisit when. driftwood run can react to file growth without a scheduler, or when a release changes how the Live log is renamed.

Glossary

Terms are defined once and linked on first use in each paragraph. Version 1, 2026-11-01.

Archive
The set of compressed Generations kept for one Live log.
Burst
A short period in which a service writes far above its normal rate, for example while it retries a failing call.
Check interval
The time between two calls of driftwood run, set by your scheduler, not by Driftwood.
Generation
A numbered Archive copy of a Live log. Generation 1 is the newest.
Live log
A log file that an application still writes to.
Overshoot
The amount by which a Live log exceeds max_size before a check notices; at most one Check interval of writes.
Rotation
The act of renaming a Live log to Generation 1 and starting an empty Live log. Compression and deletion follow it but are not part of it.
Size trigger
The Trigger that fires when a Live log is above max_size.
Time trigger
The Trigger that fires when the schedule time is reached, whatever the file size.
Trigger
A condition that makes a Live log due: size above max_size, or the schedule time reached. Driftwood has two, the Size trigger and the Time trigger.
