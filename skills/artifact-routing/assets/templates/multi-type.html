Rotate the logs of one application

The goal is a log folder that Driftwood rotates by itself: each Rotation moves the Live log to a compressed Generation, and no more than 7 Generations stay.

Done when driftwood check prints 0 files due, and the log folder holds app.log plus Generations named app.log.1.gz and up. If you have not used Driftwood before, rehearse the cycle in the Tutorial first.

Before you start

The examples use /var/log/app. Replace it with your folder. This guide adds driftwood.toml, renames app.log, adds compressed Generations and adds one scheduled job.

Steps

Run the steps in order. After each one, compare the output with the line that starts You should see. If it differs, stop and go to the failure table.

  1. Copy the log folder

    Make a copy now, because step 5 renames app.log.

    cp -a /var/log/app /var/log/app.bak

    On Windows use Copy-Item C:\logs\app C:\logs\app.bak -Recurse. You should see: no output.

  2. Create the config

    Run this in the log folder. It writes a starter config; see CMD1 for its options.

    cd /var/log/app
driftwood init

    You should see:

    wrote ./driftwood.toml

    If you see error: driftwood.toml already exists, keep your file and go to step 4.

  3. Check the keys

    Open driftwood.toml and make sure the [rotate] table holds these values, which are the defaults. The meaning of each key is in the configuration table; keep is CFG2 and max_size is CFG4.

    [rotate]
path = "."
keep = 7
compress = "gzip"
max_size = "50MB"
schedule = "daily"

  4. Check the config

    Run this before the first Rotation. It changes nothing.

    driftwood check

    You should see a valid config and the Live log marked as due. Exit code 1 here only means a file is due.

    config: ./driftwood.toml ok
due  ./app.log   62MB > max_size 50MB
1 file due

    If the first line differs, do not continue. error: config not found is F1.

  5. Rotate once

    Changes your files

    This renames app.log to Generation 1 and starts a new app.log. Do it only if step 4 printed config: ./driftwood.toml ok.

    driftwood run

    You should see:

    1 file rotated, 0 skipped

    If you see error: another run holds the lock, go to F4.

  6. Schedule it

    Driftwood does not start itself. Call driftwood run every hour. It rotates a Live log only when it is due, so an hourly call is safe.

    crontab -l > crontab.bak
(crontab -l 2>/dev/null; echo '0 * * * * cd /var/log/app && driftwood run') | crontab -

    You should see: no output. crontab -l ends with the line you added. On Windows use schtasks [UNTESTED].

Verify the result

Read the state instead of trusting the last output.

driftwood check
ls /var/log/app

You should see:

config: ./driftwood.toml ok
ok   ./app.log   0KB
0 files due
app.log  app.log.1.gz  driftwood.toml

Undo

Undo in reverse order. You can stop after any step.

  1. Remove the schedule

    crontab crontab.bak

    You should see: no output. crontab -l no longer lists driftwood run.

  2. Restore a rotated Live log

    This writes Generation 1 to a new file and never overwrites app.log. Add --generation N for an older one.

    cd /var/log/app
driftwood restore app.log

    You should see:

    restored app.log.1.gz -> app.log.restored

Rotate your first logs

You rotate and compress a log file in a throwaway Sandbox, so nothing outside it changes. You finish with a compressed Generation, a restored copy of it and a driftwood.toml you wrote yourself. There are six steps, and each ends with the output you should see. To do the same on a real folder, use the How-to guide.

What you will do

  • S1. Create the Sandbox with a 2,000-line log file.
  • S2. Create the config with driftwood init.
  • S3. Lower max_size to 64KB and keep to 3, so the log is large enough to rotate.
  • S4. Check before you run, without changing a file.

Do the steps

  1. Create the Sandbox with a sample log

    Step 1 of 6 · Changes: creates the folder driftwood-sandbox and app.log inside it.

    macOS and Linux (bash, zsh)

    mkdir driftwood-sandbox && cd driftwood-sandbox
for i in $(seq 1 2000); do echo "2026-11-01T10:00:00Z INFO request $i ok"; done > app.log

    Windows (PowerShell 7)

    mkdir driftwood-sandbox; cd driftwood-sandbox
1..2000 | ForEach-Object { "2026-11-01T10:00:00Z INFO request $_ ok" } | Set-Content app.log

    List the folder with ls.

    You should see: one file.

    app.log

  2. Create the config file

    Step 2 of 6 · Changes: creates driftwood.toml in the Sandbox.

    driftwood init

    You should see:

    wrote ./driftwood.toml

    Print the file with cat driftwood.toml. It uses TOML, a plain text format of key = value lines.

    You should see: the five keys of the [rotate] table with their defaults.

    [rotate]
path = "."
keep = 7
compress = "gzip"
max_size = "50MB"
schedule = "daily"

  3. Set the limits

    Step 3 of 6 · Changes: rewrites driftwood.toml.

    Your log is 81KB, far below the default limit of 50MB, so nothing would rotate. Replace the config with a lower max_size (CFG4) and a smaller keep (CFG2).

    macOS and Linux (bash, zsh)

    cat > driftwood.toml <<'EOF'
[rotate]
path = "."
keep = 3
compress = "gzip"
max_size = "64KB"
schedule = "daily"
EOF

    Windows (PowerShell 7)

    @'
[rotate]
path = "."
keep = 3
compress = "gzip"
max_size = "64KB"
schedule = "daily"
'@ | Set-Content driftwood.toml

    You should see: no output.

  4. Check before you run

    Step 4 of 6 · Changes: nothing.

    Run driftwood check (CMD3).

    driftwood check

    You should see: the config accepted and the log marked as due. The exit code is 1, which here only means a file is due.

    config: ./driftwood.toml ok
due  ./app.log   81KB > max_size 64KB
1 file due

    If the second line starts with ok instead of due, repeat S1 and S3.

  5. Run the Rotation

    Step 5 of 6 · Changes: renames app.log to Generation 1, compresses it and creates a new empty app.log.

    Warning

    driftwood run rotates every Live log that is due in the folder named by path. Run it only in driftwood-sandbox.

    pwd
driftwood run --verbose

    You should see: a path that ends in driftwood-sandbox, then the report of one rotated file.

    rotated ./app.log -> app.log.1.gz
1 file rotated, 0 skipped

    Run ls again. You should see three names: app.log app.log.1.gz driftwood.toml. The new app.log is empty, and the 81KB of lines now sit in Generation 1.

  6. Restore the Generation

    Step 6 of 6 · Changes: creates app.log.restored.

    Rotation is reversible. driftwood restore (CMD4) copies a Generation back into a new file. FILE is the Live log name, and Generation 1 is the default.

    driftwood restore app.log

    You should see:

    restored app.log.1.gz -> app.log.restored

    Print the first line with head -n 1 app.log.restored (PowerShell: Get-Content app.log.restored -TotalCount 1). You should see the first line you wrote in S1.

    2026-11-01T10:00:00Z INFO request 1 ok

    If you add --generation 9, the command prints error: generation 9 not found for app.log, because the Archive holds only Generation 1.

What you learned

You wrote a driftwood.toml (S3), asked Driftwood what a run would do (S4), saw one Rotation turn an 81KB log into a compressed Generation and a fresh empty log (S5), and undid it with a restore (S6). That is the cycle Driftwood repeats on a schedule. The exact options are in the Reference, and the reason for the two triggers is in the Explanation.

Logs grow in bursts, not on a calendar

This tab answers one question: why does Driftwood rotate a Live log when it is above max_size or when the schedule time is reached, and not on time alone? A time-only rule lets a file grow by the write rate times the whole period, while the size rule caps growth at max_size plus one Check interval of writes. The price is that Generation names carry a number instead of a calendar period (L1). We ask the maintainers to review ADR-1.

A service that writes a few kilobytes an hour can write megabytes per second for a few minutes when it retries a failing dependency. A rotation rule that only looks at the clock cannot see that difference. The tab does not explain how to configure the rule; the steps are in the How-to guide and the options in the Reference.

Two goals drive the design:

  • G1. Bounded disk use. No single Live log may fill the volume between two Rotations.
  • G2. Predictable retention. The keep key counts Generations, so the number of files on disk stays fixed.

Interpretation, not measurement: we read G1 as the more important goal because a full volume stops the service, while an odd file name only costs a reader some time.

Two triggers share one check, so the earlier one wins

Your scheduler calls driftwood run every minute [SAMPLE]. Each call asks two questions about every configured Live log. If it is above max_size the Size trigger fires. If the schedule time is reached the Time trigger fires. Either one rotates the file, and the first to fire wins because Rotation resets both.

Edges: scheduler call to size check. Size check yes goes to rotate; no goes to schedule check. Schedule check yes goes to rotate; no goes to leave the file as it is. Rotate goes to the compress check. Compress yes goes to compress Generation, then to delete Generations beyond keep. Compress no goes straight to delete Generations beyond keep.

With a write rate r, a schedule period P and a Check interval c, the worst-case file size is r × P for time only, and max_size + r × c for size and time. With r = 2.5 MB/s, P = 86400 s, c = 60 s and max_size = "50MB" [SAMPLE]:

$ python -c "print(2.5*86400/1000, 'GB', 50+2.5*60, 'MB')"
216.0 GB 200.0 MB

The Overshoot is one Check interval of writes, so it does not depend on the schedule. To see which Live logs are due right now, run driftwood check.

A shorter time-only schedule still loses to the burst

Four ways to bound disk use were compared against G1 and G2.

OptionWhat it givesWhat it costsVerdict
Leave rotation to each applicationNo new toolEvery service rotates differently and many do not at allLoses on G1 and G2
Time only, short periodCalendar names, simplest ruleThe period must be tuned to the worst burst, and a file still grows by r × PStrongest alternative, loses on G1
Size onlyHard cap on file sizeA quiet service never rotates, so old lines never reach compress or keepLoses on G2
Size and time, whichever firstCap on size and a bound on ageGeneration names carry a number, not a period (L1)Chosen

Time only with a short period is the strongest alternative because it keeps names predictable and needs one rule. It loses because its bound depends on guessing the worst burst: a 5 minute period still allows r × 300 s = 750 MB at the sample rate. Time only does win on one point: names. A reader who wants "the log for Tuesday" finds it directly under a time-only rule and has to check file times under ours.

The price is paid by people who search Generations by date

Positive consequences go to the operator on call, who no longer sees a full volume from logs. Negative consequences go to whoever reads Generations later. Three limits are accepted.

  • L1. Numbered names. A Generation name carries a number, not a calendar period, so a day may span several Generations.
  • L2. Check granularity. A Live log can exceed max_size by one Check interval of writes, the Overshoot. Lowering the interval lowers the Overshoot and raises the number of runs.
  • L3. Rename window. Rotation renames the Live log, and the application keeps writing to the renamed file until it reopens its log, so lines can land in Generation 1 after the Rotation [SAMPLE]. A service that reopens its log on a signal avoids it.

Limit

The bound in G1 holds only while driftwood run is actually called. If the scheduler stops, both triggers stop. A Live log that Driftwood cannot read ends the run with error: permission denied on /var/log/app, and G1 is not met until the permission is fixed.

ADR-1 records the choice of two triggers

ADR-1. Rotate on size and on time.

Status: Accepted · Date: 2026-10-28 · Decided by: Driftwood maintainers · Supersedes: none [SAMPLE]

  • Context. A Burst of 2.5 MB/s fills 216 GB in one day under a daily rule [SAMPLE]. Goals G1 and G2 apply.
  • Decision. We will rotate a Live log when it is above max_size or when its schedule time is reached, whichever comes first.
  • Consequences. Positive: bounded files, fixed Generation count. Negative: L1, L2, L3.
  • Revisit when. driftwood run can react to file growth without a scheduler, or when a release changes how the Live log is renamed.

Glossary and abbreviations

Shared by all four tabs. One definition per term. Version 1.0, 2026-11-01.

Archive
The set of compressed Generations kept for one Live log.
Burst
A short period in which a service writes far above its normal rate, for example while it retries a failing call.
Check interval
The time between two calls of driftwood run, set by your scheduler, not by Driftwood.
Dry run
A run that reports what it would do and changes no file.
Generation
A numbered Archive copy of a Live log, such as app.log.1.gz. Generation 1 is the newest.
Live log
A log file that an application still writes to, such as app.log.
Lock file
The file .driftwood/lock, which stops two runs from rotating at once.
Overshoot
The amount by which a Live log exceeds max_size before a check notices; at most one Check interval of writes.
Rotation
The act of renaming a Live log to Generation 1 and starting an empty Live log.
Sandbox
A throwaway folder where a tutorial runs, so no real file is touched.
Size trigger
The Trigger that fires when a Live log is above max_size.
State file
The JSON file that records the last Rotation time of each Live log.
Time trigger
The Trigger that fires when the schedule time is reached, whatever the file size.
Trigger
A condition that makes a Live log due: size above max_size, or the schedule time reached.
