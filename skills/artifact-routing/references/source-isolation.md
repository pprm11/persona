# Isolate sources for separate audiences

Use this when separate pieces of one request have different audiences or access (for example a client version and an on-call version). Ordinary single-audience work skips it.

When separate pieces have different audiences or access, the coordinator prepares a separate allowlisted source bundle for each. Include only the minimum facts needed, with stable neutral source IDs, enough context to interpret each fact, its applicability and verified access for that audience. Unclassified information is not externally releasable. Preserve the requested scope and authorization; ordinary single-audience work follows the usual path.

Dispatch each writer in a fresh, non-inherited context containing only that audience's bundle and assignment. Do not pass a mixed prompt, transcript, handoff, files, links, attachments, another draft, memory or shared summary. Do not give the writer tool access that can recover broader information: use an actual access boundary, not a prompt instruction as a substitute. Never put another recipient's marker into a negative example or a warning. Redacting a shared draft does not establish isolation.

Use a native Codex or Claude isolated dispatch when its context and tool access can meet these boundaries. Verify those controls before dispatch; do not assume a fresh session alone restricts tools. If isolation is unavailable, prepare the separate allowed briefs and hold drafts that would require mixed access. Do not fall back to drafting them in the shared context.

The coordinator vets every free-text bundle field, including audience, use and assignment, as well as each source and its access; tags alone do not establish safety. This text helper drafts and checks copy only. Other media and renderers receive only scoped content released after review.

For a native dispatch, run `python -I scripts/scoped_writer.py codex` or `python -I scripts/scoped_writer.py claude` from the skill directory, supplying exactly one vetted JSON bundle on stdin: `{"audience":"...","use":"...","category":"...","assignment":"...","sources":[{"id":"S1","text":"...","allowed_for":["..."]}]}`. The helper rejects unauthorized or duplicate sources before launch, removes access lists from the writer input, uses an empty temporary working directory, disables configured tool paths, and rejects unexpected native events. Its stdout is a sensitive coordinator receipt containing the submitted input, hash, command, observed session ID, event types and response. Store it only where authorized. CLI compatibility and confinement must be verified in the actual environment; a rejected or unsupported invocation is a hold, not permission to relax controls. The script requires a compatible native CLI and authentication; the native binary is found through the environment variable `SCOPED_WRITER_<NAME>`, then the PATH; if the native authentication is unavailable, configure an independent API key and hold the dispatch. The native process still needs access to its service, and this mechanism does not itself prove platform confinement. The coordinator independently checks semantic support and coverage of the ledger; structural checks do not prove either.

Independently check each draft and its metadata, logs and attachments against its own bundle. Map every substantive factual claim and imperative to an allowed source within its scope; remove or qualify unsupported costs, causes, impacts, status and promises. Perform a manual semantic check as well as any string check. Verify restricted source content is absent from the client input and output, and present in the on-call input and output when required. Return one discrete piece per audience to the authorized requester; do not merge or automatically publish them.

If the requester asks to see the versions side by side, give them a separate comparison only to the extent they may see all the material shown. Compare what each reader needs to do, the primary category, a concrete difference in the content and the sources that reader may receive. Keep the individual pieces usable on their own.

When a source establishes an available service but leaves the desired behavior undecided, cite it for the service and put the open question to whoever can decide. Label a historical outcome as such. A claim about the current version needs evidence from that version.
